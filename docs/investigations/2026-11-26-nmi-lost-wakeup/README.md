# NMIの取りこぼしで進行が止まる場面の調査（2026-11-26）

SFCのあるタイトルで、スタッフロールの下に流れる絵が途中から出なくなる（黒い画面に字だけが流れる）場面があり、
MesenCEの再現の問題か、原典のプログラムの動作かを調べた記録です。タイトル側の経緯は akiyan/kamaitachi-ops#87。

## 結論

- **MesenCEの不具合は見つかっていません。** 実行されているのは原典のコードで、原典のスケジューラにある競合
  （割り込みを止めずに合図の語を読んで書き戻す）で、NMIが立てた合図が消えます。
- **結果は入力のタイミングで変わります。** 手を加えていないMesenCEで、直前の入力待ちのボタンを押す遅れを60〜67フレームに変えた8通りのうち、
  6通りで止まり、2通り（61・65フレーム）では止まらずに絵が出ました。
- 起きるかどうかは、連続する2つのNMIの間隔のマスタークロック4個（約0.19マイクロ秒）の差で分かれます。NTSCの非インターレースでは
  フレームの長さが1つおきに4クロック違う（走査線240が1360クロックになるフレームがある）ので、到達したフレームによって結果が変わります。
- したがって、上流へ送る修正はありません。実機との差があるかを確かめるには、下の「実機で確かめるには」のテストROMが要ります。

## 仕組み（原典のコード）

1. シナリオのコルーチンが、VRAMへ送る仕事を登録し（`BRK #$0C` → `$00:89D3`）、終わりの合図（そのコルーチンの合図の語のビット3）を待つ。
2. 仕事はNMIの中で実行され、終わると `$00:8554` が合図を立てる（`$0332 + スロット` に `$0008` をOR）。
3. 待ちに入るスケジューラ（BRKのハンドラ、`$00:81B5`）は次の順で動く。割り込みは止めていない（NMIは止められない）。

   ```
   $00:8213  STA $22,X     ; 待つ合図を書く
   $00:8215  LDA $32,X     ; 合図の語を読む
   $00:8217  AND #$FFFC    ; 下位2ビットを消す
   $00:821A  STA $32,X     ; 書き戻す
   ```

4. NMIが `$8215` の後、`$821A` の前に入ると、NMIが立てたビット3を `$821A` が古い値で消す。合図は二度と来ず、コルーチンは待ちから戻らない。

## 測定（MesenCE、手を加えていない版）

止まる場合（押す遅れ60フレーム）の、問題のフレームでの実行位置：

| 番地 | 走査線 | 線内のマスタークロック |
|---|---:|---:|
| `$8213` STA | 224 | 1334 |
| `$8215` LDA | 225 | 8 |
| NMIの入口 `$80DA` | 225 | 108 |
| `$8217`、`$821A` | 258 | 436、460 |

`$8213` の最後のサイクルが走査線225の先頭（クロック0〜8）にかかり、その中（クロック6、`InternalRegisters::ProcessIrqCounters`）でNMIが立つ。
CPUはその命令の後では受けず、`$8215` の後で受ける。割り込まれた番地は `$00:8217`、合図の語は `$0881` → NMIの中で `$0889` → 戻った後 `$0880`。

押す遅れを変えた結果（`probe.lua`、`PROBE_DELAY`）：

| 遅れ（フレーム） | 60 | 61 | 62 | 63 | 64 | 65 | 66 | 67 |
|---|---|---|---|---|---|---|---|---|
| `$8215` の位置（走査線、クロック） | 225, 8 | NMIの後 | 225, 4 | 225, 6 | 225, 8 | NMIの後 | 225, 4 | 225, 6 |
| 結果 | 止まる | 進む | 止まる | 止まる | 止まる | 進む | 止まる | 止まる |

## NMIの時刻をずらす実験

`nmi-clock-experiment.patch` は、CPUへNMIを渡す線内のクロック（既定6）を環境変数で変える実験用の差分です（上流へ出すものではありません）。
`MESEN_TEST_NMI_HCLOCK` がクロック、`MESEN_TEST_NMI_PARITY` が0か1ならそのパリティのフレームだけに効きます。

- 全フレームを一律にずらしても結果は変わらない（コードが前のNMIに同期して動くので、相対位置が同じ）。
- 片方のパリティのフレームだけをずらすと、4〜8クロックで結果が入れ替わる（押す遅れ60フレームの場合）。

| ずらし（クロック） | −4 | 0 | +4 | +8 | +12 | +16 |
|---|---|---|---|---|---|---|
| パリティ0のフレームだけ | 止まる | 止まる | 止まる | 進む | 進む | 止まる |
| パリティ1のフレームだけ | 進む | 止まる | 進む | 止まる | 止まる | 止まる |

## 再現の手順

タイトルのROMとセーブRAMの像は利用者のものを使います（リポジトリには置きません）。像の作り方は kamaitachi-ops の `docs/sfc-save-format.md`。

```sh
PROBE_SRAM=$PWD/scene.srm PROBE_OUT=$PWD/out.tsv PROBE_DELAY=60 \
  bin/mesen-headless --home $PWD/home --timeout 900 $PWD/original.sfc docs/investigations/2026-11-26-nmi-lost-wakeup/probe.lua
grep -c '^bgtrans' out.tsv     # 0: 止まった。3: 進んだ
```

## 実機で確かめるには（未着手）

タイトルに依存しないテストROMで、NMIが命令の境界のどこで受け付けられるかを測れば、実機や他のエミュレーターと比べられます。

- WAIでNMIに同期し、次のNMIの直前に、上の4命令と同じサイクル構成の列（`STA dp,X`／`LDA dp,X`／`AND #imm16`／`STA dp,X`）を、
  開始位置を2クロックずつずらして実行する（8クロックと6クロックのサイクルの組み合わせで2クロック刻みを作る）。
- NMIのハンドラが、戻り番地（どの命令の後で受けたか）と、合図のビットが残ったかを、ずらし量ごとの表に書く。
- 表を画面に出す。MesenCEの試験（`tests/`）ではLuaでRAMの表を読んで期待値と比べる。
- フレームの長さの違い（1360クロックの走査線）の影響を分けるため、奇数・偶数フレームの両方で測る。

MesenCEと実機の表が一致すれば、この場面の動きは実機でも同じ（入力のタイミング次第）と言えます。食い違えば、その差が上流へ報告する内容になります。
