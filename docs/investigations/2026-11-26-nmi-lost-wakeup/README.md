# NMIの取りこぼしで進行が止まる場面の調査（2026-11-26）

SFCのあるタイトルで、スタッフロールの下に流れる絵が途中から出なくなる（黒い画面に字だけが流れる）場面があり、
MesenCEの再現の問題か、原典のプログラムの動作かを調べた記録です。タイトル側の経緯は akiyan/kamaitachi-ops#87。

## 結論

- **MesenCEの不具合は見つかっていません。** 実行されているのは原典のコードで、原典のスケジューラにある競合
  （割り込みを止めずに合図の語を読んで書き戻す）で、NMIが立てた合図が消えます。
- **結果は入力のタイミングで変わります。** 手を加えていないMesenCEで、直前の入力待ちのボタンを押す遅れを60〜67フレームに変えた8通りのうち、
  6通りで止まり、2通り（61・65フレーム）では止まらずに絵が出ました。
- 起きるかどうかは、連続する2つのNMIの間隔のマスタークロック4個（約0.19マイクロ秒）の差で分かれます。NTSCの非インターレースでは
  フレームの長さが1つおきに4クロック違う（走査線240が1360クロックになるフレームがある）ので、到達したフレームによって結果が変わります。
- したがって、上流へ送る修正はありません。実機との差があるかを確かめるための、タイトルに依存しないテストROMを用意しました（下の「テストROM」）。

## 仕組み（原典のコード）

1. シナリオのコルーチンが、VRAMへ送る仕事を登録し（`BRK #$0C` → `$00:89D3`）、終わりの合図（そのコルーチンの合図の語のビット3）を待つ。
2. 仕事はNMIの中で実行され、終わると `$00:8554` が合図を立てる（`$0332 + スロット` に `$0008` をOR）。
3. 待ちに入るスケジューラ（BRKのハンドラ、`$00:81B5`）は次の順で動く。割り込みは止めていない（NMIは止められない）。

   ```
   $00:8213  STA $22,X     ; 待つ合図を書く
   $00:8215  LDA $32,X     ; 合図の語を読む
   $00:8217  AND #$FFFC    ; 下位2ビットを消す
   $00:821A  STA $32,X     ; 書き戻す
   ```

4. NMIが `$8215` の後、`$821A` の前に入ると、NMIが立てたビット3を `$821A` が古い値で消す。合図は二度と来ず、コルーチンは待ちから戻らない。

## 測定（MesenCE、手を加えていない版）

止まる場合（押す遅れ60フレーム）の、問題のフレームでの実行位置：

| 番地 | 走査線 | 線内のマスタークロック |
|---|---:|---:|
| `$8213` STA | 224 | 1334 |
| `$8215` LDA | 225 | 8 |
| NMIの入口 `$80DA` | 225 | 108 |
| `$8217`、`$821A` | 258 | 436、460 |

`$8213` の最後のサイクルが走査線225の先頭（クロック0〜8）にかかり、その中（クロック6、`InternalRegisters::ProcessIrqCounters`）でNMIが立つ。
CPUはその命令の後では受けず、`$8215` の後で受ける。割り込まれた番地は `$00:8217`、合図の語は `$0881` → NMIの中で `$0889` → 戻った後 `$0880`。

押す遅れを変えた結果（`probe.lua`、`PROBE_DELAY`）：

| 遅れ（フレーム） | 60 | 61 | 62 | 63 | 64 | 65 | 66 | 67 |
|---|---|---|---|---|---|---|---|---|
| `$8215` の位置（走査線、クロック） | 225, 8 | NMIの後 | 225, 4 | 225, 6 | 225, 8 | NMIの後 | 225, 4 | 225, 6 |
| 結果 | 止まる | 進む | 止まる | 止まる | 止まる | 進む | 止まる | 止まる |

## NMIの時刻をずらす実験

`nmi-clock-experiment.patch` は、CPUへNMIを渡す線内のクロック（既定6）を環境変数で変える実験用の差分です（上流へ出すものではありません）。
`MESEN_TEST_NMI_HCLOCK` がクロック、`MESEN_TEST_NMI_PARITY` が0か1ならそのパリティのフレームだけに効きます。

- 全フレームを一律にずらしても結果は変わらない（コードが前のNMIに同期して動くので、相対位置が同じ）。
- 片方のパリティのフレームだけをずらすと、4〜8クロックで結果が入れ替わる（押す遅れ60フレームの場合）。

| ずらし（クロック） | −4 | 0 | +4 | +8 | +12 | +16 |
|---|---|---|---|---|---|---|
| パリティ0のフレームだけ | 止まる | 止まる | 止まる | 進む | 進む | 止まる |
| パリティ1のフレームだけ | 進む | 止まる | 進む | 止まる | 止まる | 止まる |

## 再現の手順

タイトルのROMとセーブRAMの像は利用者のものを使います（リポジトリには置きません）。像の作り方は kamaitachi-ops の `docs/sfc-save-format.md`。

```sh
PROBE_SRAM=$PWD/scene.srm PROBE_OUT=$PWD/out.tsv PROBE_DELAY=60 \
  bin/mesen-headless --home $PWD/home --timeout 900 $PWD/original.sfc docs/investigations/2026-11-26-nmi-lost-wakeup/probe.lua
grep -c '^bgtrans' out.tsv     # 0: 止まった。3: 進んだ
```

## テストROM（タイトルに依存しない）

`nmi_boundary_rom.py` は、上の4命令と同じサイクル構成の列を、VBlankのNMIの前後で開始位置を2マスタークロックずつずらして
96通り実行し、NMIがどの命令の後で受け付けられたかと、合図のビット3が残ったかを表にするテストROM（LoROM、32 KiB）を作ります。
ROMは生成物なので置きません。タイトルのコードやデータは使っていません。

- 各テストは、目的のフィールド（`$213F` のbit 7）のフレームで `WAI` してNMIに同期し、約1フレーム待ってから
  （`DEX`／`BNE` を9,570回）、テストごとの詰め物（`LDY #0`＝16クロックをi個、`NOP`＝14クロックを95−i個）を通って列を実行します。
- NMIのハンドラは、戻り番地を記録し、合図の語（`$3A`）のビット3を立てます。
- 結果はRAMの `$1000` から4バイトずつ（戻り番地、合図の語）。終わると `$1C` が1になり、画面に表を出します。

```sh
python3 docs/investigations/2026-11-26-nmi-lost-wakeup/nmi_boundary_rom.py nmi-boundary.sfc      # 実機・他のエミュレーター用
python3 docs/investigations/2026-11-26-nmi-lost-wakeup/run_nmi_boundary.py --binary bin/mesen-headless --expect --png screen.png
```

画面は、フィールド0、フィールド1の順に、それぞれ「受け付けた位置」96個（32個ずつ3行）と「ビット3」96個（同）です。

| 字 | NMIを受け付けた位置 |
|---|---|
| `-` | 列の前（詰め物の中） |
| `0` | 最初の `STA` の前 |
| `2` | 最初の `STA` の後 |
| `4` | `LDA` の後（合図を読んだ後：**取りこぼす**） |
| `7` | `AND` の後（**取りこぼす**） |
| `9` | 最後の `STA` の後 |
| `A`〜`F`、`+` | その後の `NOP`、さらに後 |

MesenCE（2.2.1のフォーク、2026-11-26）の表：

```
field 0 taken AAAA99999999999999999997777777777774444444444444444444222222222222222222000000000000------------
field 0 bit 3 111111111111111111111110000000000000000000000000000000111111111111111111111111111111111111111111
field 1 taken AAAAA9A99999999999999999997777777777774444444444444444444222222222222222222000000000000---------
field 1 bit 3 111111111111111111111111110000000000000000000000000000000111111111111111111111111111111111111111
```

- 取りこぼすのは `4` と `7` の31通り（62クロック＝`LDA dp,X` の38クロックと `AND #imm16` の24クロック）で、位置とビットは必ず対応します
  （`run_nmi_boundary.py` が確かめます）。
- フィールド0と1で表が3つ分（6クロック）ずれます。フレームの長さの違い（4クロック）が、どのテストが取りこぼすかを変えることがわかります。
- フィールド1の先頭に `9A9` と前後する所が1つあります。割り込みが近いときにCPUの空きサイクルの長さが変わる扱いによるものとみられ、
  実機と比べる価値のある点です。

### 実機・他のエミュレーターとの比べ方

同じROMを実機（フラッシュカートリッジ）や他のサイクル精度のエミュレーターで動かし、画面の表を上のものと比べます。

- 表の形（`9`・`7`・`4`・`2`・`0` の並びと幅）が同じで全体が左右にずれているだけなら、NMIの時刻か同期の遅れの数クロックの差です。
- 幅や並びが違えば、CPUが割り込みを見る時点か、サイクルの長さの扱いの差です。
- 食い違いがあれば、その表が上流（nesdev-org/MesenCE）へ報告する内容になります。今のところ、比べる相手の表はありません。
